Scripting Shell en Bash

Bases du scripting

Chapitre 03 — structure, exécution, sécurité, arguments

# Structure d'un script

Un script bash est simplement un fichier texte contenant des commandes, exécutées ligne par ligne, du début à la fin, sans compilation ni installation. Écrire un script, c'est automatiser ce qu'on ferait à la main dans un terminal.

Les qualités d'un bon script :

QualitéCe que ça signifie
FiableFonctionne même en cas de mauvaise utilisation ou d'erreur imprévue
CommentéLe code est annoté pour faciliter la relecture et les évolutions
LisibleLe code est indenté, les commandes sont aérées
PortableFonctionne sur tout système Linux

Anatomie d'un script — cliquez sur chaque ligne

Chaque ligne a un rôle. Cliquez pour en savoir plus.

1
#!/usr/bin/env bash
Le shebang — ligne obligatoire, toujours en première position. Indique à l'OS quel programme doit interpréter ce fichier. #!/usr/bin/env bash cherche bash dans le $PATH, ce qui le rend compatible quel que soit son emplacement sur le système.
2
Ligne vide — sépare visuellement le shebang du reste. Non obligatoire, mais recommandée pour la lisibilité.
3
# Ce script affiche la date et le nom de la machine
Commentaire — tout ce qui suit # sur une ligne est ignoré à l'exécution. Les commentaires servent à expliquer le pourquoi, pas le quoi. Le shebang lui-même (#!) est un commentaire spécial interprété par le noyau, pas par bash.
4
Ligne vide de séparation — aère le code.
5
set -euo pipefail
Options de sécurité — arrête le script sur la moindre erreur. Détails dans l'onglet Sécurité. À mettre systématiquement juste après le shebang.
6
Ligne vide.
7
echo "Date : $(date +%F)"
Commande — le corps du script. Les commandes s'écrivent une par ligne, ou séparées par ;. Ici, $(date +%F) est une substitution de commande : son résultat est inséré dans la chaîne.
8
echo "Machine : $(hostname)"
Commande — bash exécute les commandes dans l'ordre, de haut en bas. L'indentation n'a d'importance que dans les blocs if, for, etc.
↑ Cliquez sur une ligne pour voir son rôle

Le shebang en détail

#!/usr/bin/env bash ← recommandé (portable) #!/bin/bash ← fonctionne, mais suppose que bash est dans /bin #!/usr/bin/sh ← POSIX strict (pas de fonctions bash étendues)
Bonne pratique
Toujours utiliser #!/usr/bin/env bash. La commande env cherche bash dans le $PATH et le trouve quel que soit son emplacement. Sur certains systèmes, bash n'est pas dans /bin.
Note
Le shebang n'est lu que si le script est exécuté directement (./script.sh). Si on passe le script en argument à bash (bash script.sh), le shebang est ignoré — c'est bash lui-même qui interprète le fichier.

# Exécution d'un script

Deux méthodes d'exécution

bash monscript.sh

Passe le fichier directement à bash comme argument. Bash l'interprète sans tenir compte des permissions du fichier.

Ne nécessite pas chmod Utile pour tester rapidement Le shebang est ignoré Moins "propre" en production
chmod +x monscript.sh # une seule fois ./monscript.sh # exécution

Donne le droit d'exécution au fichier, puis l'exécute comme un programme. Le shebang est lu et c'est l'interpréteur désigné qui est utilisé.

Méthode standard en production Le shebang est respecté chmod +x à faire une seule fois
Attention — le ./ est obligatoire
Sans le ./, bash cherche le script dans les dossiers du $PATH — et ne le trouve pas. Le dossier courant n'est jamais dans le $PATH par défaut (pour des raisons de sécurité).
monscript.sh # ERREUR : command not found ./monscript.sh # CORRECT : cherche dans le dossier courant

Le script s'exécute dans un sous-shell

Quand un script est lancé, bash crée un processus enfant séparé. Ce sous-shell a son propre environnement.

Shell courant (terminal)
ville="Paris"
export PAYS="France"
./monscript.sh # lance le sous-shell ↓
Sous-shell (monscript.sh)
echo $ville # (vide) — variable locale non transmise
echo $PAYS # France — variable exportée ✓
cd /tmp # ne change PAS le dossier du terminal
# .bashrc n'est PAS chargé
Conséquences du sous-shell
  • Les variables locales du terminal ne sont pas disponibles dans le script (sauf si export)
  • Les modifications du script (variables, cd…) n'affectent pas le terminal
  • Le script ne charge pas .bashrc — il n'a pas d'environnement interactif

Mini-TP — Premier script

1
Créer le dossier de travail :
mkdir -p ~/scripting
2
Créer le script :
nano ~/scripting/d.sh
3
Contenu du script :
#!/usr/bin/env bash set -euo pipefail date +%F # affiche la date au format AAAA-MM-JJ
4
Rendre exécutable et lancer :
chmod +x ~/scripting/d.sh ~/scripting/d.sh # 2026-05-13
Note — date +%F
date +%F est un raccourci ISO 8601 équivalent à date +%Y-%m-%d.

# Sécuriser un script

Par défaut, bash continue l'exécution même si une commande échoue. C'est dangereux dans un script : une suppression de fichier ratée, une variable non définie, un pipe cassé — tout peut passer inaperçu.

On active des options de sécurité en début de script avec set. Cliquez sur chaque option pour les détails :

set -e
errexit
Arrête le script si une commande échoue
Dès qu'une commande retourne un code de sortie non nul (≠ 0), le script s'arrête immédiatement. Sans cette option, bash continue et exécute les commandes suivantes même si la précédente a raté.
rm /fichier-inexistant # code retour 1 echo "Cette ligne ne s'exécute pas" ← arrêt ici
set -u
nounset
Arrête si une variable non définie est utilisée
Sans cette option, utiliser $variable_inexistante donne simplement une chaîne vide — silencieusement. Avec -u, bash s'arrête avec un message d'erreur explicite.
echo $nom_mal_ecrit # bash: nom_mal_ecrit: unbound variable → arrêt
set -o pipefail
pipefail
Propage les erreurs dans les tubes
Sans cette option, le code de retour d'un tube (cmd1 | cmd2) est celui de la dernière commande, même si une commande précédente a échoué. Avec pipefail, toute erreur dans le tube est détectée.
cat /fichier-inexistant | grep motif # sans pipefail : $? = 0 (grep a "réussi") # avec pipefail : $? = 1 (cat a échoué)
set -x
xtrace
Debug : affiche chaque commande avant exécution
Bash affiche chaque commande précédée de + au moment où elle est exécutée. Indispensable pour déboguer. À désactiver en production — la sortie devient très verbeuse.
+ echo "Bonjour" Bonjour + date +%F 2026-05-13

La combinaison standard

#!/usr/bin/env bash set -euo pipefail # à mettre dans tout script sérieux # suite du script...
Bonne pratique
Commencer tout script avec set -euo pipefail. Les erreurs silencieuses deviennent des arrêts explicites — les bugs sont bien plus faciles à trouver.

Désactiver temporairement une option

Quand une commande est connue pour échouer sans que ce soit un problème, on désactive -e le temps de son exécution :

set +e # désactive -e (le + inverse le -) grep "motif" fichier.txt # peut retourner 1 si rien trouvé set -e # réactive -e
Attention — set -x en production
set -x est très utile pour déboguer mais produit une sortie massive. Ne l'activer que pendant la mise au point. En production, utiliser plutôt bash -x script.sh ponctuellement.

Code de retour — $?

Toute commande Linux retourne un code de retour à la fin de son exécution :

0
Succès — la commande s'est exécutée sans erreur
1
Erreur générale
2
Mauvaise utilisation (ex : dossier introuvable pour ls)
126
Fichier non exécutable
127
Commande introuvable
128+N
Arrêt par signal N (ex : 130 = Ctrl+C, 137 = SIGKILL)
ls /etc echo $? # 0 ← succès ls /dossier-inexistant echo $? # 2 ← échec
Attention
$? ne contient que le code de la dernière commande exécutée. Si tu exécutes une autre commande entre les deux (même un echo), tu perds la valeur. Stocker $? dans une variable si tu en as besoin plus tard : code=$?

# Variables spéciales & Arguments

Bash définit automatiquement des variables spéciales qu'on ne peut que lire, pas modifier. Les plus importantes permettent de récupérer les arguments passés au script.

Tableau des variables spéciales

$0
Nom du script (tel qu'il a été appelé : ./monscript.sh ou chemin complet)
$1 … $9
Arguments passés au script — 1er, 2e… 9e argument
${10} …
Arguments au-delà du 9e — les accolades sont obligatoires
$#
Nombre d'arguments passés au script (sans compter $0)
"$@"
Tous les arguments, chacun cité séparément — à utiliser dans les boucles et pour passer des arguments à une autre commande
"$*"
Tous les arguments en un seul mot (séparés par le 1er caractère de $IFS) — rarement utile
$?
Code de retour de la dernière commande exécutée (0 = succès)
$$
PID du shell courant — utile pour créer des fichiers temporaires uniques : /tmp/mon_script_$$.tmp
$!
PID du dernier processus lancé en arrière-plan (commande &)

Exemple concret — salutation.sh

Contenu du script :

#!/usr/bin/env bash set -euo pipefail echo "Script : $0" echo "Arg 1 : $1" echo "Arg 2 : $2" echo "Nb args : $#" echo "Tous : $@"

Appel et résultat :

./salutation.sh Alice Bob Charlie Script : ./salutation.sh Arg 1 : Alice Arg 2 : Bob Nb args : 3 Tous : Alice Bob Charlie

Valider les arguments — bonne pratique

On contrôle toujours le nombre d'arguments en début de script pour donner un message d'erreur utile :

#!/usr/bin/env bash set -euo pipefail # Vérifier qu'on a bien reçu exactement 1 argument if [[ $# -ne 1 ]]; then echo "Usage : $0 <prénom>" >&2 exit 1 fi echo "Bonjour, $1 !"
Bonne pratique
Les messages d'erreur s'envoient sur stderr avec >&2. Ainsi, ils restent visibles même si la sortie standard est redirigée vers un fichier.

$@ vs $* — la différence

# Appel : ./script.sh "Alice Dupont" Bob # "$@" — deux arguments séparés, espaces préservés for arg in "$@"; do echo $arg done # Alice Dupont # Bob # "$*" — un seul mot fusionné (rarement ce qu'on veut) for arg in "$*"; do echo $arg done # Alice Dupont Bob
Règle simple
Utiliser toujours "$@" (avec guillemets). C'est presque toujours ce qu'on veut. "$*" n'a des cas d'usage que très spécifiques.

# Quiz de révision

Testez vos connaissances — cliquez sur la bonne réponse.

1. Quelle est la première ligne obligatoire d'un script bash ?
#!/usr/bin/env bash est la forme recommandée. Le shebang (#!) doit être en première position, sans espace. env cherche bash dans le $PATH, ce qui le rend portable sur tous les systèmes.
2. Tu lances ./monscript.sh depuis ton terminal. Dans quel shell la variable $ville définie dans le terminal est-elle visible ?
Un script s'exécute dans un sous-shell. Les variables locales du terminal ne sont pas transmises. Seules les variables exportées (export ville) sont visibles dans le script.
3. Quelle option de set arrête le script dès qu'une commande échoue ?
set -e (errexit) arrête le script dès qu'une commande retourne un code non nul. -u gère les variables non définies, -x est le mode debug, pipefail gère les erreurs dans les tubes.
4. Pourquoi le ./ est-il obligatoire devant ./script.sh ?
Bash cherche les commandes dans les dossiers listés dans $PATH. Le dossier courant (.) n'y figure pas par défaut pour des raisons de sécurité. Le ./ dit explicitement "ce fichier, dans le dossier courant".
5. Tu appelles ./salutation.sh Alice Bob Charlie. Que contient $# ?
$# contient le nombre d'arguments passés au script, sans compter $0 (le nom du script). Ici 3 arguments : Alice, Bob, Charlie.
6. Que vaut $? après une commande qui s'est exécutée avec succès ?
Par convention Unix, 0 signifie le succès. Tout autre valeur (1 à 255) indique une erreur. C'est ce code que set -e surveille : dès qu'il est ≠ 0, le script s'arrête.
7. Tu appelles ./script.sh "Alice Dupont" Bob. Quelle variable itère correctement sur les deux arguments en préservant l'espace ?
"$@" (avec guillemets) préserve chaque argument comme une entité séparée, espaces inclus. Sans guillemets, $@ est découpé sur les espaces : "Alice Dupont" deviendrait deux arguments. "$*" fusionne tout en un seul mot.
